- **A `mode: block`/`require:`/`forbid:` rule could fail open behind a heredoc-shaped line that never actually opened one** (#442). `jit_strip_heredoc_body()` (#432) treated any `<<WORD`-shaped text as a real heredoc operator whenever a later line happened to equal WORD, with no awareness of quoting or comments -- so `echo "<<EOF"` followed by an unrelated later `EOF` line, or a `# <<EOF` comment line, hid every line between them from the rules that only ever see `fold_full`. A `. /dev/stdin <<EOF` dot-sourced heredoc was hidden too: its body is executed code, the same reason `bash <<EOF`/`sh <<EOF`/`source <<EOF` are already exempt, but a lone `.` cannot survive the denylist lookup's own normalization, which erases every character outside `[a-z0-9_]` before the lookup runs. Fixed by requiring a genuine quote-free, non-comment operator line before anything is treated as a real heredoc opener, and by detecting `.` as a dot-source directly against the raw line rather than through the normalized lookup. Self-review found the same gap for a trailing comment on an otherwise real command line (`true # <<EOF`), fixed the same way as the whole-line case, and a reviewer found that a single-quoted argument can legitimately open on one physical line and close several lines later -- the quote is still genuinely open on every line in between, so the quote-tracking state is now carried forward across the whole command text rather than reset at the start of each line. Every change narrows what gets stripped -- it can only leave MORE text visible to a rule than before, never less, so #432's own tests (a heredoc body is not command text) are unaffected and still pass, and the new tests run across every awk engine found on the machine (awk, gawk, mawk), the same discipline this file already applies to other character-by-character logic in it.
