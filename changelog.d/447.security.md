- **The heredoc-body sink allowlist checked the WHOLE line for a known data sink, so a decoy sink sharing the line with the real heredoc operator -- separated by `;` or `&&` -- could still hide a non-sink command's heredoc body from a `forbid:`/`~`/`mode: block` rule** (#447, carried forward from the v0.12.0 gate-3 security audit round 2). `jit_heredoc_opener_is_known_sink()` never bound the `<<` operator to the specific simple command it trails, so `cat > /dev/null </dev/null; bash <<EOF` matched the `cat` pattern anchored earlier on the same line and stripped `bash`'s own heredoc body as if `bash` itself were the sink -- the same shape the round-1 fake-arithmetic-opener bug could then hide behind, since an unrelated sink decoy ahead of a `(( y = 1<<EOF ))` line made that fake opener match too. The closing-delimiter extraction also kept only a single optional quote or backslash character on each side of the bare identifier, so a delimiter bash itself builds by concatenating several quoted/escaped/bare pieces -- `<<EOF"X"` (bash closes at `EOFX`), `<<EOF-1` (bash closes at `EOF-1`, since `-` and digits are ordinary bare word characters), `<<E\OF` (bash collapses the backslash and closes at `EOF`) -- closed at the wrong line for the stripper, either leaving a real sink's own data wrongly visible or never finding a close at all.
  Fixed by binding the sink allowlist check to just the clause the operator sits in, bounded by the nearest `;` or `&` on either side, and by replaying bash's own word-formation rule one character at a time to compute the real closing delimiter -- a bare run of ordinary characters, a single-quoted run, a double-quoted run (where an escaped double-quote, backslash, dollar or backtick collapses to the literal character), or a single backslash-escaped character outside quotes, concatenated with no gap. Binding the operator to its own clause also closes the arithmetic-decoy combination: the fake opener's own clause has no sink in it either way, so it is never treated as a real heredoc. `jit_heredoc_opener_has_danger_token()` now runs on that same clause too, which is more precise than the whole line and never less conservative, since a pipe or substitution in an unrelated earlier clause has nothing to do with this heredoc's own command.
  The #442 changelog entry's claim that "an unrecognized command keeps its body visible by default" was not true for any of the shapes above -- each one reached a RECOGNIZED sink's allowlist match through the decoy, not an unrecognized command at all. This entry corrects that scope: the allowlist direction was always safe, but it was being evaluated against the wrong clause.
