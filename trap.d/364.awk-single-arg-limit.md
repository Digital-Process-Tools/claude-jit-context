Observed on PR #369 (fix/364), CI job 101365175629, hooks (ubuntu-latest, shard 1/1),
all 26 suites that exercise scripts/pre-tool-hook.sh failed identically across every
awk engine in the matrix (gawk, mawk, nawk, one-true-awk), each with:

  scripts/pre-tool-hook.sh: line 80: <enginebin-path>/awk: Argument list too long

Line 80 is the LC_ALL=C awk invocation. Every suite passed locally on macOS first.

Mechanism: scripts/pre-tool-hook.sh (and pre-prompt-hook.sh, pre-path-hook.sh,
post-tool-hook.sh) build their awk program as ONE shell argument -- a double-quoted
concatenation of every JIT_AWK_* macro from scripts/common.sh, immediately followed
(no space) by a single-quoted literal awk source block. Bash concatenates two
adjacently-quoted strings with no space between them into one word, so this is a
single argv entry, not several.

Linux's execve() enforces MAX_ARG_STRLEN = 32 * PAGE_SIZE = 131072 bytes as a cap on
any SINGLE argv or envp string -- separate from, and far smaller than, the total
argv+envp size most people mean by "ARG_MAX". macOS enforces no such per-argument cap
(only the much larger total). So a single argument that grows past 131072 bytes fails
loudly on Linux and silently says nothing is wrong on macOS.

Before this lane's #364/#365 fix, pre-tool-hook.sh's single argv string measured
129890 bytes -- 1182 bytes under the Linux cap. The fix's own added code (a small awk
function plus documentation comments) pushed it to 132965 bytes, 1893 over. Nothing
about the FIX's logic was wrong; the margin that had existed before simply ran out.

Cost: a full round trip through a real CI run (a maintainer-side agent triaged the
failed job, diagnosed the mechanism, and reported it back) before the actual byte
count was ever measured. Could have been caught locally, on macOS, in the same
session that wrote the fix, with a one-line-of-reasoning static check: nothing about
this bug depends on actually invoking awk or exec()-ing anything -- it is a fact about
the byte length of a fixed string in the source file, knowable without running the
process that would fail.

Confirmed by reproduction: reverting scripts/pre-tool-hook.sh to the exact pre-trim
commit and re-measuring gave back the identical 132965 figure CI's own stderr implies
(129890 unchanged baseline + 1893 bytes over the 131072 cap = 132965 - 131072 = 1893
over, matching the earlier by-hand measurement exactly).

Fixed here by trimming the added comments (reasoning kept in git blame / the PR body
instead of inline) and adding tests/test-awk-arg-max-369.sh, a pure byte-count check
(no exec, no awk invocation, runs identically on every platform) asserting every
macro-concatenating hook stays under 131072 bytes for its single awk-program argument.

Not decided here, and flagged for whoever curates this: this class of hook (a big
literal awk program handed to awk as a raw command-line argument, rather than via
awk -f against a generated tempfile) has NO margin against this failure mode by
construction -- any repository that keeps adding to these hooks' shared macros or
their own literal awk source will eventually cross 131072 bytes again, on Linux only,
regardless of how carefully any one PR trims its own comments. Whether that argues for
a structural change (delivering the program via a tempfile and -f instead of argv) is
a design decision, not a hotfix, and is out of scope for the PR that hit this.
