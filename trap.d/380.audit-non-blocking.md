Three non-blocking findings from the v0.9.0 release audit (gate 3, round 1). None of
them stopped the tag; each is logged here rather than filed, per the routing rule for a
row that can ship behind a fragment.

1. scripts/common.sh -- JIT_TOOL_ALIASES is "" in two different worlds, and nothing
   downstream can tell them apart: "host.sh could not be read or sourced" and "every
   registry row's alias column is legitimately empty". The file's own comment names the
   collapse. JIT_HOST_REFUSAL_STATE is set and exported by common.sh and no hook reads
   it; jit-doctor.sh does not mention the host at all. What it costs on a degraded read:
   on Codex, apply_patch stops normalising to Edit/Write, so a mode: block tools rule
   silently stops refusing -- the #364 defect, reachable again, with no line in
   hooks.log, no injected notice and nothing in the diagnostic. Reachability is low:
   host.sh sits beside common.sh in the install. Ranked misreports.

2. tests/test-hook-tmpfile.sh section C -- the skip branch does not set
   SKIPPED_SECTIONS=1, unlike section A, so a skipped section contributes zero PASS and
   zero FAIL and the suite still exits 0. A green guard and an absent one render
   identically. That shape is unchanged since v0.8.0 and was cosmetic there. This delta
   makes it load-bearing: pre-tool-hook.sh's own comment names section C as the sole
   exerciser of the new `awk -f <(printf ...)` fallback, and changelog.d/371.fixed.md
   repeats the claim. So the one automated exercise of a new path in the hottest hook can
   go to zero assertions and say nothing. The open question is whether chmod 555 removes
   the write bit for the owner on the windows-latest runner. Ranked misreports.

3. scripts/pre-tool-hook.sh, the else arm running awk -f on a /dev/fd path -- Windows
   coverage could not be determined, which is not the same as uncovered. tests.yml runs
   four windows-latest shards, so the platform is nominally covered; what is unknown is
   whether the one leg reaching this branch actually reaches it there, for the reason in
   item 2. changelog.d/371.fixed.md says as much itself: verified on macOS, the Linux and
   Windows claim reasoned from the mechanism rather than observed. If awk -f on a /dev/fd
   path fails under MSYS2, a hook whose whole contract is never fail hard emits an awk
   diagnostic into a stranger's session while already degraded. One Windows CI run in
   which section C's assertions actually execute would settle it. Ranked
   fails-to-preserve.

Item 2 is the one worth curating first: it is the reason item 3 cannot be answered.
