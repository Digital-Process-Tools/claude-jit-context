Observed while re-verifying red/green for a source-guard fix in
Digital-Process-Tools/claude-jit-context #388.

`.git` is shared across every `git worktree add`-created worktree of the same
repository. A `git stash push -- <file>` that reports "No local changes to save"
(because the named file already matches HEAD) followed by `git stash pop` in the same
worktree does NOT necessarily do nothing -- `stash pop` is not scoped to what the
immediately-preceding `push` (didn't) create, it pops whatever is at the top of the
repository-global stash list. In this case that was `stash@{0}`, a leftover stash from
an entirely different, unrelated branch (`chore/shfmt-reformat`), presumably left by
another session or a previous run in a sibling worktree of the same clone.

The result: `git stash pop` applied that unrelated stash's changes into my worktree and
produced merge conflicts across roughly 11 files I had never touched (scripts/host.sh,
scripts/jit-misses.sh, scripts/post-tool-hook.sh, scripts/rebuild-tsv.sh,
scripts/stop-hook.sh, and six tests/*.sh files). Nothing about the `stash push`'s "No
local changes to save" message warned that the follow-up `pop` would touch anything --
that message is only about what push found to save, not about what's already sitting on
the stack.

Cost: one recovery round-trip. `git status --short` to see the conflict list,
`git diff -- <the one file I actually meant to touch>` to capture my own in-flight
uncommitted edit before touching anything else, `git reset --hard HEAD` (safe here
because it only discards the working tree/index, never a stash object -- the unrelated
stash entry was still `stash@{0}` in `git stash list` afterward, untouched), then
`git apply` to restore my captured diff.

How I confirmed the fix worked and nothing was silently dropped: `git stash list`
before and after the reset showed the same two entries (`stash@{0}` on
`chore/shfmt-reformat`, `stash@{1}` from an unrelated `release-run` stash-before-checkout
message) in both stack positions.

Not sure whether this belongs as a jit-context rule about `git stash` inside a
worktree specifically, or a broader "worktree-shared git state" rule that would also
cover things like `git bisect`, reflog entries, or hooks installed at the `.git`
level rather than per-worktree. Logging it and leaving that decision to /oss:curate.
