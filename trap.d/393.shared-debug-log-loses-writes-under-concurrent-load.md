Observed while diagnosing #393 (suites flaking under concurrent worktree load).

First instrumentation attempt appended a one-line debug record from inside `stop-hook.sh`
to a single fixed path shared by every concurrent invocation across four worktrees
(`>> /path/to/one/shared/debug_awk_rc.log`). Under the same heavy concurrent load the
issue itself is about, that shared log LOST WRITES: grepping it by session ID afterward
showed some sessions (`sess-a` in one round, `sess-s3` in another) with zero matching
lines at all, even though the test driving them ran in every round and the earlier/later
sections in the same run logged fine. No error was printed anywhere -- the `>>` itself
never failed loudly, the line just was not there afterward.

Cost: most of an investigation round trusting a false negative (assuming the debug print
was never reached, i.e. an early return elsewhere in the hook, when the code path was
actually reached every time and only the write to the SHARED log was unreliable).

Fix applied within the same investigation: write debug state into a file already private
to that invocation's own fixture -- `"${CLAUDE_PROJECT_DIR}/dbg0.txt"`, one per `mktemp -d`
project, since each test fixture already gets its own directory in this repo's own
suites. Once every writer had a private target, every invocation's record showed up
reliably across the same concurrency and load that had been dropping the shared file's
lines.

Not sure whether this is `bash`'s own `>>` failing to guarantee atomicity for the write
sizes involved once dozens of processes contend for one inode's append offset on this
filesystem (APFS, macOS), or something else in the pipeline losing the write before it
reaches the file. Did not chase further because the actual finding (#393) did not need a
shared log at all -- every suite in this repo already has a private `mktemp -d` per
fixture, and using it instead made the shared-log question moot for the task at hand.
Logging this so the next agent who reaches for "just tee everything into one file" while
stress-testing something concurrent does not spend the same round rediscovering it.
