Editing `scripts/common.sh` with `supertool edit:@-` to append after `JIT_AWK_ENVELOPE_SYSMSG=` (a bash single-quoted assignment whose closing character is a lone quote character on its own line, immediately followed by EOF) repeatedly produced a corrupted file: `bash-check` reported "reached EOF without closing quote" and the edit was rolled back both times before the cause was found.

Root cause: in the TOML payload, `old`/`new` fields were written with the content's own trailing quote and the TOML literal-string delimiter (three quote characters) glued onto the SAME line, e.g. a line reading exactly `}` then a line reading exactly three quote characters. TOML's multi-line literal string parser takes the FIRST occurrence of three consecutive quote characters as the closing delimiter, so all three were consumed as the delimiter and the content's own trailing quote (the bash string terminator the file actually needs) was silently dropped from BOTH `old` and `new`. `old` still matched (as a strict prefix of the real file content minus its last byte), so the edit "succeeded" at the anchor stage and only failed later at `bash-check`, with a confusing "reached EOF" message that gave no hint the dropped byte was self-inflicted.

Fix: when content must end with a literal single quote right before the TOML closing delimiter, put the content's own trailing quote on its OWN line, separated by a newline from the closing delimiter line.

This reproduced cleanly (two failed attempts, same symptom) before the fix was found by manually simulating the substitution in Python and running `bash -n` against it, which showed the simulated substitution (done correctly) was syntactically fine -- proving the corruption was in how the edit payload was written, not in the target content itself.

Confirmed via a second, unrelated instance in the same session: the exact same "three delimiter quote characters on one line as content's own trailing character" mistake, this time with a trailing backslash (a bash line continuation) instead of a trailing quote, was refused outright by supertool's own payload linter with a clear message naming a literal block ending with a backslash immediately before its closing delimiter -- worth noting because that case is caught up front with a good error, while the trailing-quote case is not: it silently drops the byte and only fails much later, off in bash-check, with no hint of the real cause.

A third instance, while writing THIS very fragment: prose describing the delimiter itself (three quote characters, spelled out) closed the surrounding literal block early and produced a TOML parse error rather than a silent corruption -- caught immediately this time because the delimiter sequence appeared mid-line rather than glued to real content at a line boundary. Worked around here by describing the delimiter in prose instead of typing it.

Not filed as a rule and not judged worth one -- just the sequence of symptom, root cause and fix, logged in case the pattern recurs.
