#424 fixed the -v backslash-escape defect (a CLAUDE_PROJECT_DIR-derived path passed to
awk via -v, whose escapes awk's -v silently decodes) in scripts/pre-tool-hook.sh's
tools_base/vocab_base. Explore's self-review pass over that PR found the identical
defect, still live, in scripts/jit-misses.sh: the generic-words-file path is passed to
awk BOTH as a real positional command-line argument (unescaped, seen verbatim as
FILENAME) and via `-v genfile=`/`-v genname=` (escape-processed). The only way the awk
program recognizes "this is the generic-word list, not the log" is
`genfile != "" && FILENAME == genfile` -- so a backslash-bearing path (a checkout, or a
--generic-words override, under a Windows-shaped directory) mangles `genfile` while
the real `FILENAME` stays unmangled, the comparison never matches, and the
generic-word list's lines get read as if they were hooks.log records instead of
populating `generic[]`. Generic-word filtering silently degrades to "off" with no
error, indistinguishable from an unconfigured list. `-v logfile="$LOG"` carries the
same defect but only for display text (the printed "log: ..." line), cosmetic only.

Fix shape, when someone picks this up: route genfile/genname/logfile through ENVIRON
the same way #424 routed JIT_BASE, tools_base and vocab_base -- LOG/GENERIC_WORDS_FILE
are already ordinary bash variables built from $CLAUDE_PROJECT_DIR, so `export` them
(or read `ENVIRON["..."]` directly if they are already inherited unassigned) rather
than continuing to build a second, `-v`-decoded copy for comparison purposes.

Not fixed as part of #424 itself: different file, different subsystem (a maintainer
tool jit-misses.sh reads and reports on, not a hook that decides a rule), and pinning
it needs its own fixture (a log padded so jit-misses.sh's generic-word pass actually
runs, plus a positional-vs--v divergence case) rather than reusing #424's own test
shape.
