Writing awk into these scripts.sh JIT_AWK_* string blocks: a dynamic regex (a STRING
passed to match()/gsub(), not a /literal/ regex) that needs to match a literal backslash
inside a bracket expression needs the runtime string to carry TWO backslash bytes, not
one.

Observed: `q3 = sprintf("%c", 92)` (one backslash byte) then `qclass = "[" q1 q2 q3
"]?"` used as a dynamic-regex bracket. Running the hook produced: `awk: nonterminated
character class [^<]<<-?[ \t]*['"\]?[` and exit 2 -- the whole rule engine refused every
call for the rest of the session (fails closed, per this hook's own #397 posture, so it
was loud rather than silent, but still cost a full test-suite run to notice: 205/343
tests failed with "the rule engine could not evaluate this call").

Root cause, as best determined: this awk's dynamic-regex compiler treats a lone
backslash inside a bracket expression as an escape introducer for whatever follows it
(here, the class-closing bracket), consuming it -- so the bracket never closes and the
whole ERE fails to compile. This is DIFFERENT from a /literal/ regex, where q1/q2
(apostrophe, double-quote, no backslash) worked fine with the same bracket-building
approach.

Fix: `q3 = sprintf("%c%c", 92, 92)` -- two backslash bytes, so the escape-consuming pass
collapses them back to one literal backslash inside the class, and the real closing
bracket right after it closes the class.

Confirmed by: reverting to one backslash reproduced the exact error above; the two-byte
form ran clean and the full suite (353/353) passed.

Not sure whether this generalizes to every dynamic regex in this codebase or is specific
to one-true-awk's implementation (LC_ALL=C pin was active; not tested against gawk with
this exact construct) -- worth someone checking both engines explicitly if another
dynamic-regex-with-backslash is ever written here.
