Observed: three `supertool edit`/`paste` calls, issued without a `cd` prefix in their
own Bash call, landed in the MAIN CLONE (/Users/floriandavid/Documents/claude-jit-context)
instead of the worktree I was supposed to be editing
(/Users/floriandavid/Documents/jit-wt/437). This happened right after a call that DID
start with `cd .../jit-wt/437 && ...` -- the cwd reset between Bash calls (stated in the
environment system-reminder) is easy to forget mid-task once a few calls in a row have
all been correctly prefixed.

Cost: two script edits (scripts/common.sh, scripts/rebuild-tsv.sh) plus one stray
directory write (data/generic-words/README.md) landed in the main clone. Caught only
because a fixture test run afterward produced output inconsistent with what the edits
should have changed -- `bash -x` tracing showed the OLD code path still running in the
worktree, which is what triggered the investigation. Fixed by `git status`/`git diff
--stat` in the main clone (confirmed only those three paths were touched), `git checkout
--` on the two tracked files, and `rm -rf` on the stray untracked directory.

How to avoid: every `supertool edit:@-`/`paste:@-`/`batch:@-` call in a worktree-based
task needs its OWN `cd <worktree> &&` prefix, with no exception for "I just cd'd two
calls ago." The op's own output has a `[branch: ...]` line at the end precisely so this
is checkable after the fact -- read it before trusting that a write landed where
intended, especially right after any call that did NOT start with `cd`.
