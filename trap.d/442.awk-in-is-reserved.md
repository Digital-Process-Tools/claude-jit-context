While extending jit_heredoc_quote_states() in scripts/common.sh (issue #442, cross-line quote-state carry-over), the function was first written as:

    function jit_heredoc_quote_states(lines, n, in,    i, state) {
      state = 0
      for (i = 1; i <= n; i++) {
        in[i] = state
        state = jit_heredoc_line_exit_state(lines[i], state)
      }
    }

Using `in` as a parameter/array name. `in` is an awk reserved word (it is the keyword used in `for (key in array)` and in the `(key in array)` membership test), and both gawk and the system `awk` on this machine accepted the script without a syntax error -- there was no parse-time complaint at all -- but the function silently produced garbage, and every caller downstream of it broke.

Cost: running `bash tests/test-pre-tool-hook.sh` after introducing this went from 374/374 passing to 163/374 passing, 211 failed, with no single obviously-related failure message pointing at the cause -- the failures looked like a broad, unrelated regression across completely different test sections, not like a syntax error in one small new function. It took reading the diff again and recognizing `in` as a keyword (rather than re-running with a debugger or bisecting) to find it; renaming the parameter to `qin` immediately restored 374/374 (then 375/375, 378/378 as further tests were added).

Confirmed by: the fix (rename only, no other change) made every failing assertion pass again, with no other code touched.

Not sure how general this is -- it may be worth a rule for "awk reserved words that are legal-looking identifiers and compile without error" (also candidates, untested here: `getline`, `print`, `printf`, `length` is actually a builtin function name and might be a separate case). Logging it as observed rather than deciding whether/how it becomes a durable rule.
