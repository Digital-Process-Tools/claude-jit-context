Observed while fixing #447 (jit_heredoc_opener_is_known_sink's whole-line sink
check should have been bound to the operator own clause, and was).

A reviewer (Explore spawn, self-review round) reported that
`hdcmd; python3 -c "x=1; tee y" <<EOF\nheredocforbid now\nEOF` still silently hides
the heredoc body from a forbid:/mode: block rule even after the #447 clause-binding
fix landed, framing it as a regression the #447 fix was supposed to close. I
reproduced it end to end through the real hook (scripts/pre-tool-hook.sh, with a
synthetic hdcmd/heredocforbid fixture matching tests/test-pre-tool-hook.sh's own
convention) and confirmed the body IS stripped (the `heredocforbid` payload never
reaches fold_full, so a forbid: row never fires on it).

But it is NOT a #447 regression. I reproduced the identical payload against
scripts/pre-tool-hook.sh as it existed at bda0282 -- the commit immediately before
any of my #447/#455 changes, with the OLD whole-line (not clause-bound) sink check
-- and it ALSO hides the body there. Root cause: jit_heredoc_opener_is_known_sink()'s
five sink patterns (cat>, tee, supertool, git commit -F -, gh --body-file -/-F -) are
plain awk EREs matched against a text span (the whole line before #447, the operator
own clause after #447) with ZERO quote-state tracking. A quoted ";" inside a
legitimate argument to a NON-sink command (python3 -c "x=1; tee y") still leaves the
literal substring "; tee y" sitting in the text being matched, and the `tee` regex
-- anchored on `(^|[;&|])[ \t]*tee[ \t]+...` -- cannot tell that the ";" and the
"tee" it is anchored against are both inside a double-quoted Python string rather
than being real shell syntax. jit_heredoc_opener_has_danger_token() has the identical
blind spot for `|`, `$(`, backtick, `>(`, `<(` (though that direction is the SAFE one
for a deny-style rule -- a quoted danger token only makes the override MORE likely to
fire, never less, so it cannot itself become a bypass the way the sink patterns can).

What I did fix in this same round (genuinely #447-scoped, and kept): a bare,
quote-UNAWARE scan for ";"/"&" in jit_heredoc_clause_at() itself -- the function that
decides WHERE the clause boundary falls, as opposed to whether the regex matching
WITHIN that clause is quote-aware -- could forge a fake boundary off a quoted ";"/"&"
and truncate the clause wrong in either direction. Fixed by threading a per-line
quote state (jit_heredoc_quote_states()'s own quote_in[i]) through
jit_heredoc_clause_at() and only treating a ";"/"&" as a boundary when the state at
that character is 0. Verified this closes a real (non-security, over-cautious)
precision bug: `hdcmd; tee ";" <<EOF` (tee writing to a file literally named ";")
used to have its clause truncated to `" <<EOF`, losing "tee" entirely and so NOT
being recognized as a sink (keeping real, safe sink data needlessly visible to a
forbid: rule) -- now correctly returns the whole clause and classifies it as a sink.
Covered by a new test in tests/test-pre-tool-hook.sh ("a quoted ; inside the sink own
argument does not forge a fake clause boundary").

What is NOT fixed, and is the actual subject of this trap: making the five sink
regexes (and the danger-token checks) genuinely quote-aware -- i.e. blanking out or
skipping quoted spans before running the EREs, rather than matching raw text -- is a
separate, larger change touching every pattern in jit_heredoc_opener_is_known_sink()
and jit_heredoc_opener_has_danger_token(), pre-dates #447 entirely, and was out of
scope for the two issues (#447, #455) this lane was dispatched to fix. Per
skills/manager/phases/findings.md's ranking table this is a `misreports` row (the
hook answers "nothing to block" when a forbid:/block: rule was never evaluated
against text bash will actually run) -- non-blocking, "can ship behind a trap.d
fragment" -- which is why this is a trap fragment rather than a filed issue.

Confirmed by: direct awk-level reproduction (jit_heredoc_opener_is_known_sink()
called directly with the quoted-tee clause, returns 1), and end-to-end through the
real hook on both HEAD (post-#447) and bda0282 (pre-#447), using a throwaway
CLAUDE_PROJECT_DIR fixture mirroring tests/test-pre-tool-hook.sh's own hdcmd/
heredocforbid convention -- not asserted from the awk trace alone.

Candidate shape for whoever curates this: the fix likely wants a shared helper that
blanks every character inside a single/double-quoted span of a line/clause to a
placeholder BEFORE any of the five sink patterns or the danger-token index() checks
run against it -- jit_heredoc_clause_at()'s own new instate[] quote-tracking loop in
this same commit is most of the machinery already, just needs to run once more,
earlier, over the text actually handed to the matchers rather than over the raw
clause.
