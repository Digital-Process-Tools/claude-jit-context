The new regression test for #459 (tests/test-no-heredocs-459.sh) builds its
detector as `awk '...' "$1" | grep -nE -- "$PATTERN" || true`. The `|| true` is
there so the pipeline's overall exit status is never non-zero just because
`grep` found no match (a clean file is the expected common case, and `set -o
pipefail` is not in effect in this script -- only `set -uo pipefail` is, and
`pipefail` is the missing one here) -- but it also means `awk` failing for an
unrelated reason (the file vanished between `git ls-files scripts` and the
read, a permissions problem, anything) produces the exact same empty string as
a file that was genuinely read and found clean. The live sweep then prints "no
tracked file under scripts/ opens a real here-document" identically for
"checked every file and all were clean" and "could not actually read one of
them." Caught by the oss:auditor self-review spawn on this issue, filed as
non-blocking/misreports rather than fixed in the same pass, since it is a
narrow, pre-existing shape (`detect_heredoc_lines()`'s own `|| true`) rather
than something this diff's live sweep loop can plausibly hit today -- the file
list comes from `git ls-files` moments earlier in the same run.

What would close it: check `[ -r "$1" ]` before scanning, or capture awk's own
exit status separately from grep's (e.g. `awk ... > "$tmp"; awk_rc=$?; grep -nE
... "$tmp"`), so an unreadable-file case renders distinguishably from a clean
one rather than collapsing into the same empty string. Possibly a case for a
small reusable "two outcomes is not three outcomes" pattern across this
repo's other `|| true`-guarded pipelines, if curation turns up siblings of this
same shape elsewhere in tests/.
