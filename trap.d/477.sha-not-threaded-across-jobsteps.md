Observed during self-review of the #477 fix (second Explore spawn, strict
finding-format re-ask). The fix (`REF="${SOURCE_REF:-HEAD}"` in
tests/test-release-branch-461.sh, reading the job-level $SOURCE_REF env var)
closes the exact gap #477 named -- a hard-coded `--ref HEAD` diverging from
what the workflow actually publishes on a workflow_dispatch run with an
older `ref=` input -- but it narrows rather than fully closes the class.

In `.github/workflows/release-branch.yml`, the "Build the release tree" step
resolves `$SOURCE_REF` to a frozen `sha=$(git rev-parse --verify
"${SOURCE_REF}^{commit}")` and builds from that sha. The later "Equivalence
test the compiled scripts (#461)" step (test-release-branch-461.sh) is never
handed that resolved sha -- it independently re-reads `$SOURCE_REF` and
re-resolves it itself inside build_release_tree.py. If a dispatch's `ref=`
input names a moving ref (a branch, not a tag or sha) and that ref moves
between the two steps, the equivalence test can still build and check a
different commit than the one the first step already built and `publish`
will later push -- the same class of silent-wrong-tree bug #477 described,
with a narrower window (between two steps in one job run) instead of none.

Not acted on in the #476/#477/#478 lane: closing this fully means threading
the already-resolved `sha` from the "Build the release tree" step's own
`steps.build.outputs.sha` into the equivalence-test step (a job `outputs:`
wire-up plus a CLI flag or env var on test-release-branch-461.sh), which is
a workflow-level change beyond what #477 asked for and risks widening this
lane's diff into territory #477's own issue text did not scope.

Worth curation's attention: whether this is worth a follow-up issue, and
whether `workflow_dispatch`'s `ref=` input is realistically ever a moving
branch name in practice for this repo (the input's own description says
"Tag (or sha)", which would make this window theoretical rather than live).
